# Working in Astrology Engine

This repository separates an immutable Rust chart runtime from native dataset
preparation and the example HTTP adapter:

```text
JPL inputs -> tools/ (native preparation) -> HDCHEB01 bytes
                                                |
                                                v
caller-supplied bytes -> src/ (chart and Sun-search calculations)
                             ^
                             |
                  examples/cloudflare-worker/ (R2 and HTTP)
```

Keep storage, network access, configuration and caches at the host/adapter
boundary. ANISE belongs to the native builder; the default runtime must remain
usable in Wasm without it. The runtime's `generation` feature exposes shared
math and format code to the builder; it does not make the runtime a downloader.

Use functional programming with explicit inputs and effects at boundaries;
use reactive functional state where applicable. Use ESM for JavaScript, avoid
OOP and JavaScript classes. When grilling, ask one question at a time.

Read only the guidance for the area you are changing; root instructions also
apply there:

| Task | Scoped guidance | Human-facing context |
| --- | --- | --- |
| Runtime math, format or chart behavior | [src/AGENTS.md](src/AGENTS.md) | [Architecture](docs/architecture.md) |
| Acquisition, generation or parity harnesses | [tools/AGENTS.md](tools/AGENTS.md) | [Tools guide](tools/README.md) |
| R2 loading, HTTP integration or local Wasm checks | [Worker AGENTS.md](examples/cloudflare-worker/AGENTS.md) | [Worker runbook](docs/worker-runbook.md) |

The brand site and learning courses are maintained separately in the private
`jacksteamdev/astrology-engine-website` repository. Their writing guides,
application checks and browser adapter belong there; this repository owns
the reusable runtime, native tools and public integration examples.

Choose checks by the boundary changed. The [regular workflow](.github/workflows/verify.yml)
is the command reference; the [full-data workflow](.github/workflows/full-data.yml)
covers explicit regeneration and pinned-dataset parity. Root workspace commands
do not include the Worker, and `cargo test` alone does not run its structural
Wasm harness. Consult the scoped files before claiming those checks passed.

Keep structural tests, local Wasm execution, frozen-baseline parity, full
regeneration and hosted checks distinct in reports. None alone establishes
independent astronomical accuracy. Regression fixtures record outputs from a
previous version of the astrology engine. Preserve their inputs and hashes;
never regenerate expected values from changed code just to make tests pass.

## Swiss Ephemeris prohibition

Never install, import, link, invoke, vendor, or otherwise use Swiss Ephemeris,
including `sweph`, `swisseph`, `pyswisseph`, or other wrappers. This applies to
runtime code, development tools, data generation, tests, comparisons, and
validation. Never introduce samples, fixtures, datasets, or derived reference
artifacts generated by it. Documentation may name and discuss this prohibition;
that exception does not authorize executable examples or dependencies.

Install the tracked hook after cloning:

```sh
git config --local core.hooksPath .githooks
```

The pre-commit hook checks staged code, dependencies, configuration and fixtures.
Prose documentation is exempt; executable files under documentation directories
are not. CI runs the same check. Retain permitted JPL inputs and recorded 
regression outputs from the previous engine.

## Worktree conventions

- Use one branch and worktree per independent implementation task; reuse the
  existing worktree for related work. Inspect the checkout path, branch, status,
  and worktree list before editing. Preserve unrelated changes without stashing
  or moving them automatically.
- Create new task worktrees at `<primary-checkout>/.worktrees/<task-slug>/`.
  Resolve the primary checkout from the first entry of
  `git worktree list --porcelain`, including when working from a linked worktree;
  do not nest worktrees beneath the current linked checkout.
- Name task branches `feat/<slug>`, `fix/<slug>`, or `chore/<slug>`. Base independent
  work on the refreshed remote default branch when available. Without a remote,
  use local `main` and report that base. If refreshing fails, report the failure
  before choosing a potentially stale base. Identify the required base commit
  explicitly for dependent work; uncommitted changes do not follow a new worktree.
- Report the worktree path and branch before implementation. Run edits, checks,
  and commits in that worktree.
- Install dependencies only for the area being changed. Keep build outputs,
  mutable caches, and dataset generation outputs isolated per worktree. Where
  supported, explicitly reference shared immutable dataset inputs rather than
  copying them or sharing mutable output directories.
- Follow the scoped guidance and checks for the affected boundary. At handoff,
  report the branch, commits, checks, and PR if one exists. Retain task worktrees
  until their work is integrated.
- Before cleanup, inspect active users, uncommitted changes, untracked and ignored
  data, and commits needing preservation. Use normal `git worktree remove`.
  Ask before forced removal or unlocking, explaining potential loss or disruption.
